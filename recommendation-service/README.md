# Recommendation Service

Java 21 + Spring Boot 4.1 gRPC-сервис для ранжирования городских мероприятий. Сервис не читает базу данных: API Service передаёт статистику посещений пользователя и список мероприятий-кандидатов. Контракт расположен в `src/main/proto/recommendations.proto`.

## Запуск

```bash
./gradlew bootRun
```

Сервер слушает порт `50051`. Для другого порта задайте переменную окружения `SPRING_GRPC_SERVER_PORT`.

Образ можно собрать и запустить отдельно:

```bash
docker build -t recommendation-service .
docker run --rm -p 50051:50051 recommendation-service
```

## Вызов

Метод `recommendations.v1.RecommendationService/GetRecommendations` принимает один запрос и возвращает один ответ. Для локальной проверки включена gRPC Reflection (`grpc-services`), поэтому `grpcurl` может прочитать контракт с сервера:

```bash
grpcurl -plaintext localhost:50051 list
```

Пример запроса:

```bash
grpcurl -plaintext -d '{"categoryStats":[{"categoryId":"7","visitCount":3},{"categoryId":"12","visitCount":1}],"candidates":[{"eventId":"11","categoryIds":["7"],"startsAt":"2030-11-10T18:00:00Z"},{"eventId":"12","categoryIds":["7","12"],"startsAt":"2030-11-12T18:00:00Z"},{"eventId":"13","categoryIds":["12"],"startsAt":"2030-11-01T18:00:00Z"}],"limit":2}' localhost:50051 recommendations.v1.RecommendationService/GetRecommendations
```

Ожидаемый порядок: мероприятие `12` с баллом `4`, затем мероприятие `11` с баллом `3`. В JSON Protobuf поля `int64` представлены строками.

Некорректный запрос, например `{"limit":0}`, возвращает gRPC-статус `INVALID_ARGUMENT` с описанием нарушений. Ошибки вычисления или самого валидатора возвращают `INTERNAL`; подробности остаются в журнале сервера.

## Правила ранжирования

Для каждого кандидата балл равен сумме числа посещений пользователя по его категориям. Повтор одной категории внутри кандидата учитывается один раз. Сортировка: балл по убыванию, затем ближайшая дата начала, затем ID мероприятия. Возвращаются первые `limit` результатов. При пустой истории все баллы равны нулю и порядок определяется датой и ID. При пустом списке кандидатов ответ пустой.

API Service должен собрать статистику по броням `ATTENDED`, передать будущие мероприятия со статусом `SCHEDULED` и исключить мероприятия с активной бронью пользователя. Сервис возвращает только ID и баллы; API Service получает карточки мероприятий из своей БД и сохраняет порядок результата.

В текущей интеграции API Service вызывает метод из `GET /api/recommendations?limit=10`. Он выбирает до 200 ближайших подходящих мероприятий, исключает активные брони и отправляет статистику посещений по категориям. В Compose адрес сервиса — `recommendation:50051`; при локальном запуске Python API — `localhost:50051`.

Правила входных и выходных сообщений описаны в `.proto` через Protovalidate. При генерации Python-клиента из общего контракта нужно также предоставить импорт `buf/validate/validate.proto` и соответствующий сгенерированный Python-модуль. Сам gRPC-клиент не обязан запускать валидатор: запрос проверяется на сервере.
